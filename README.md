# MAX Chat

Веб-интерфейс для отправки и получения текстовых сообщений в мессенджере **MAX** 
через сервис [GREEN-API](https://green-api.com/max). 
Прототип интерфейса — [web.max.ru](https://web.max.ru/).

Тестовое задание на должность «Фронтенд-разработчик React».

## Возможности

- Вход по учётным данным GREEN-API (`idInstance`, `apiTokenInstance`) с проверкой авторизации инстанса
- Создание чата по номеру телефона получателя
- Отправка текстовых сообщений с оптимистичным отображением (статусы: отправляется / отправлено / ошибка)
- Получение ответов через long-polling с автоматическим подтверждением уведомлений
- Повтор отправки сообщения по клику при ошибке
- Индикатор потери соединения с автоматическим переподключением
- Адаптивная вёрстка (на мобильном показывается либо список чатов, либо переписка)
- Доступность: навигация с клавиатуры, `Enter` — отправка, `Shift+Enter` — перенос строки, озвучивание входящих для скринридеров
- Демо-режим на моках (MSW) — можно проверить весь сценарий без реального GREEN-API

## Стек

- **React 19** + **TypeScript** (strict)
- **Vite 8** — сборка и dev-сервер
- **TanStack Query** — запросы, кэш, поллинг, ретраи
- **Zustand** — клиентское состояние (сессия/учётные данные)
- **Tailwind CSS v4** — стили
- **Vitest** + **Testing Library** + **MSW** — unit/integration-тесты
- **Playwright** — сквозные (e2e) тесты
- **ESLint** (+ `eslint-plugin-boundaries`) и **Prettier**
- **GitHub Actions** — CI

## Локальный запуск

```bash
npm install       # установка зависимостей
npm run dev       # dev-сервер на http://localhost:5173
```

Для работы приложения понадобятся учётные данные инстанса GREEN-API
(`idInstance`, `apiTokenInstance`) — их вводит пользователь на экране входа.

## Демо-режим (без GREEN-API)

На экране входа есть переключатель **«Демо-режим»**. Если реального инстанса
GREEN-API нет, включите его — и можно прокликать весь сценарий на замоканном
API:

- вход проходит с любыми данными (поля автоматически заполняются `demo`/`demo`);
- отправленное сообщение получает автоответ;
- сообщение со словом «ошибка» или текст `/fail` эмулируют ошибку отправки
  (чтобы проверить повтор).

Как это устроено:

- мок реализован на [MSW](https://mswjs.io/) и перехватывает запросы к GREEN-API
  прямо в браузере — реальные запросы никуда не уходят;
- код мока грузится **лениво отдельным чанком** только при включении режима, поэтому
  основной бандл не раздувается;
- выбор режима сохраняется в `localStorage` и переживает перезагрузку.

Это демонстрация UI на фейковых данных, а не настоящая интеграция — она нужна,
чтобы проверить интерфейс без доступа к инстансу GREEN-API.

## Архитектура

Проект организован по методологии **Feature-Sliced Design**. Слои (сверху вниз):

```
src/
  app/        # провайдеры, глобальные стили, входная точка приложения
  pages/      # страницы (экраны)
  widgets/    # композиционные блоки UI
  features/   # пользовательские сценарии (отправка, приём, вход)
  entities/   # бизнес-сущности (сообщение, чат)
  shared/     # переиспользуемое: api-клиент GREEN-API, ui-kit, утилиты
```

Правило импортов — слой может зависеть только от слоёв строго ниже себя. Это
проверяется автоматически линтером (`eslint-plugin-boundaries`), нарушение
границ роняет CI.

## Взаимодействие с GREEN-API

- **Отправка** — `POST .../sendMessage` (`chatId`, `message`).
- **Получение** — HTTP API: long-polling `GET .../receiveNotification`, после
  обработки уведомление подтверждается через `DELETE .../deleteNotification/{receiptId}`.
- Номер получателя нормализуется в `chatId` формата `{phone}@c.us`.

### CORS

GREEN-API отдаёт `Access-Control-Allow-Origin: *`, поэтому запросы идут
**напрямую из браузера** — серверный прокси не требуется.

### Безопасность учётных данных

`idInstance`/`apiTokenInstance` вводятся пользователем и хранятся только на его
устройстве (в рамках сессии). Токен не покидает браузер и никуда, кроме самого
GREEN-API, не отправляется. Это осознанное ограничение фронтенд-приложения без
бэкенда — для продакшена запросы стоит проксировать через сервер, чтобы токен не
попадал в браузер.

## Тестирование

- **Unit / integration** — Vitest + Testing Library, сеть GREEN-API замокана через MSW.
  Покрыты утилиты, сторы и хуки (вход, отправка, повтор, приём по long-polling).

  ```bash
  npm run test
  ```

- **E2E** — Playwright прогоняет полный сценарий (вход → создание чата → отправка →
  получение ответа) в headless-браузере. Все запросы к GREEN-API перехватываются и
  мокаются, реальный аккаунт и живая отправка не используются.

  ```bash
  npx playwright install chromium   # один раз
  npm run test:e2e
  ```

## CI

GitHub Actions на каждый push в `main` и pull request запускает два джоба:

- **quality** — `typecheck → lint → format check → unit-тесты → build`
- **e2e** — установка браузера и прогон Playwright с выгрузкой отчёта
